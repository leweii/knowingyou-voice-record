# 零网络运行时验证

S21 验收标准要求"零网络验证结果记录在案"，spec 原文允许用 Little Snitch 或 `nettop -p <pid>` 两种方式之一。这台环境没有 Little Snitch（需要额外安装第三方软件），改用 `nettop` + `lsof` 两个系统自带工具做了一次真实验证，结果如下。

## 验证方法

1. 用 Release 配置构建、`open` 启动 `KnowingYou.app`（ad-hoc 签名，见 S21 决策记录的"补充实测"一条），拿到运行中的 PID。
2. `nettop -p <pid> -L 45 -s 2 -x`：以 CSV 格式采样 45 次、每次间隔 2 秒，覆盖约 90 秒的运行窗口。
3. `lsof -p <pid> -i`：单独确认该进程当前持有的所有网络类文件描述符（TCP/UDP socket）。
4. `lsof -p <pid>`（不带 `-i`）：确认该进程全部文件描述符的类型分布，交叉核对第 3 步的结论。

## 结果

**`nettop` 输出的 45 个采样点里，没有任何一条为 `KnowingYou` 进程输出连接明细行**——只重复打印了列头，说明整个 90 秒观察窗口内，这个进程没有建立过一次 TCP/UDP 连接（哪怕是失败的连接尝试也会在 nettop 里留下一条记录）。

**`lsof -p <pid> -i` 对这个 PID 没有任何输出**——即这个进程当前没有持有任何网络 socket 文件描述符，一个都没有。作为对照，同一次 `lsof` 快照里，这台机器上其它正常运行的应用（Chrome/QQ/微信/Slack/Air/claude 等）都能看到大量 `ESTABLISHED`/`LISTEN` 状态的真实网络连接——不是 `lsof` 本身没抓到数据，是 `KnowingYou` 这个进程确实没有。

`lsof -p <pid>`（全部文件描述符）显示这个进程只持有：系统框架的只读文件（SwiftUI/AppKit/Carbon 等 dylib 与资源包）、`/dev/null`（标准输入输出）、以及一个指向它自己保存目录 `~/Documents/Knowing You` 的目录句柄——没有任何 socket 类型的描述符。这和 `scripts/check-no-network.sh` 的静态扫描结论（源码里不存在 `URLSession`/`Network.framework`/`CFNetwork` 等联网 API 的引用）完全吻合：不仅源码里没写联网代码，运行时也确实一次都没有尝试联网。

## 这次验证的范围（诚实说明）

- 观察窗口是应用**空闲状态**（启动后弹出首次引导窗口，未做任何录音）下的 90 秒，不包含 spec 原文里提到的"含一次完整录音"的场景——因为这台环境的麦克风 TCC 权限会被系统错误归因给宿主 "Air" 进程而不是 KnowingYou 本身（见 CLAUDE.md、S07 决策记录），无法在这里真正触发一次端到端的录音。
- 不过这恰好是对"零遥测/零联网"最有意义的一种验证方式：等录音这类主动功能反而不是关键，一个真正"零联网"的应用，在完全空闲、什么都不做的时候，同样应该没有任何后台联网行为（分析上报、崩溃日志上传、更新检查等常见的"意外联网"来源，通常正是在空闲时段周期性触发的）——而这次观察到的是真正意义上的"零"：不是"频率很低没抓到"，是这个进程压根不持有任何网络类文件描述符。
- 更长时间、包含真实录音全流程的验证，仍然建议 Jakob 在自己的 Mac 上用 Little Snitch 再做一次，尤其是覆盖到麦克风/系统音频 tap 真正工作的那段代码路径。

## 结论

在这个环境能做到的范围内（空闲状态、90 秒、系统自带工具），零网络的结论得到了运行时验证支持，不只是源码静态扫描的结论。S21 验收标准里"零网络验证结果记录在案"这一条，从"完全没做"更新为"用系统自带工具在空闲态下完成了一次，真实录音路径的验证留给 Jakob 在自己机器上补充"。
