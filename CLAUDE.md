**Read this before writing any pure/static logic on a `View`-conforming type and unit-testing it directly (discovered in S15, still relevant for S17/S18)**: on this SDK/toolchain, `struct Foo: View` implicitly infers `@MainActor` onto `Foo`'s members — including `static` ones that touch no view state at all. Calling such a member from a test that isn't itself `@MainActor` doesn't fail to compile (the isolation-crossing check apparently doesn't get enforced across a `@testable import` module boundary) — it crashes the whole `xctest` host process at runtime instead (`EXC_BREAKPOINT` in `_swift_task_checkIsolatedSwift`/`dispatch_assert_queue_fail`), which is a much worse failure mode than a compile error. Fix: mark any such pure static helper `nonisolated` explicitly (see `LevelMeterView.litSegmentCount`/`.thresholds`). Don't assume "it's just a pure function, it can't need isolation" — the compiler's inference doesn't agree unless you say so.

**Read this before absolutely-positioning (`.position(x:y:)`) a sub-view that itself contains other absolutely-positioned elements (discovered in S16)**: `.position()` places a view within its *parent's implicit coordinate space*, which is derived from where its siblings' own `.position()` calls put them — not clipped to whatever `.frame()` you apply afterward. Nesting a `ZStack` (or any container) that uses window-absolute `.position()` coordinates inside a *smaller* sub-view silently breaks: the sub-view's implicit content bounds balloon out to include those absolute coordinates, and a later `.frame(height: 44)` doesn't rescue it — children still render wherever their absolute `.position()` said, which can be far outside the visible frame. This is exactly what made `NotesToolbar` invisible on the first screenshot pass (see S16's decision record) until its internal y-coordinate was changed from the spec's window-absolute `342.5` to a value relative to its own local frame. When copying an element's position straight out of a UI spec's coordinate table, get very clear on *which view's coordinate space* that number is relative to before using it — it is almost never safe to reuse a top-level absolute coordinate inside a smaller, separately-composed sub-view. When in doubt, prefer ordinary top-down `VStack`/`HStack` layout for anything containing an `NSViewRepresentable` or another absolutely-positioned container, and reserve `.position()` for leaf-level siblings that already share one unambiguous coordinate space (e.g. a handful of icons at the top of a window, like `PillView` and `NotesView`'s own header).

**S17 (`HotkeyManager`) discovered that `KeyboardShortcuts.Shortcut.isTakenBySystem` (and the `.system` list it's built from) are `internal` to the package, not `public`** — despite being exactly what you'd want for validating a just-recorded combo against reserved system shortcuts. `ShortcutFormatting.isCommonlyReservedBySystem` is a small hand-maintained substitute (Spotlight, App Switcher, the screenshot combos, Force Quit, Quit/Close/Hide/Minimize) — not exhaustive, but the package's own hotkey registration already fails silently/harmlessly for genuinely system-reserved combos, so this is a UX nicety (a friendlier alert) rather than a correctness gap. Also: "click elsewhere to cancel" recording is implemented as "any click cancels, including on the button itself" — precisely distinguishing inside/outside needs view-geometry bookkeeping for an interaction that can't be verified with real clicks in this environment anyway.

**S19's localization mechanism is worth understanding before you add any new user-facing string.** Since S02, every `DesignSystem` component's text parameter has been typed `LocalizedStringKey`, not `String` — a decision made early, for exactly this moment. That means a plain string literal passed to `Text`, `SectionHeader`, `SettingsRow`, `OutlinedButton`, `Button`, `TextField`'s placeholder, `.alert(_:)`, etc. is automatically looked up in `Resources/Localizable.xcstrings` (keyed by the literal zh-Hans string itself, since that's the catalog's `sourceLanguage`) — **no code change needed**, just an entry in the catalog. Language switching itself was already wired in S04 (`GeneralSettingsView` sets `UserDefaults.standard.set([lang], forKey: "AppleLanguages")` and prompts for a restart) — S19 just gave the catalog something to resolve. Two things this does NOT cover automatically:
1. **Plain `String` properties on AppKit objects** (`NSAlert.messageText`, `NSMenuItem` titles via `addItem(withTitle:)`, `NSWindow.title`, `NSSavePanel`/`NSOpenPanel` titles/prompts, `UNMutableNotificationContent.title`/`.body`, `UNNotificationAction` titles) — these need an explicit `String(localized: "...")` call at the site to pull from the catalog; SwiftUI's automatic `LocalizedStringKey` inference doesn't apply outside SwiftUI view initializers.
2. **String interpolation** (`Text("停止录音  \(elapsed)")`) — technically SwiftUI can turn this into a format-style `LocalizedStringKey` too, but hand-authoring the exact catalog key it generates is fragile and can silently fall back to the source language. The pattern used throughout this codebase instead: `String(format: String(localized: "停止录音  %@"), elapsed)`, wrapped in `LocalizedStringKey(...)` if the destination parameter needs one. Search the codebase for `String(format: String(localized:` to find the existing examples before inventing a new pattern.

Also deliberately **not** localized, on purpose: `KnownApps.displayNameKey` (app brand names), the `.md` file format's `[标记]`/`[截图]`/`[事件]` markers and the "截图"/"录音" filename fallbacks (these are baked into files on disk — switching UI language must never change what a filename or an existing note's markup looks like), and the low-frequency event text `RecordingSession`/`AppState` write into notes bodies (device-changed/paused/screenshot-failed messages) — a straightforward candidate for a future pass, skipped here to keep the increment of work reasonable. See S19's decision record for the full reasoning.

**S18 (`ScreenshotMarker`) uses `SCStreamConfiguration`, not `SCScreenshotConfiguration`**, for `SCScreenshotManager.captureImage(contentFilter:configuration:)` — the latter is macOS-26-only and this app's deployment target is 14.4; the former has backed this same `captureImage` overload since 14.0. It also picks the "frontmost" window using real z-order from `CGWindowListCopyWindowInfo(.optionOnScreenOnly, kCGNullWindowID)` cross-referenced by `CGWindowID`, since `SCShareableContent.windows` carries no documented ordering guarantee. Screen-recording permission is presumed to hit the same TCC-misattribution wall as microphone permission does on this machine (S07) — not independently re-verified, but there's no reason to expect otherwise — so this whole pipeline is code-reviewed only, never run. Fixed in passing while touching this code: S13 had declared `AppState.resolveManualRecordingSourceApp` but `MeetingCoordinator` never actually set it (the property wasn't even part of the `MeetingRecordingControlling` protocol it depends on), so "手动开始录音 uses a currently-detected meeting app's name" silently never worked since S13 landed — now fixed, with `RecordingInfo` gaining a `sourceBundleIDPrefix` field this fix (and `ScreenshotMarker`'s own window-matching) both needed.

**Testing UI changes on this machine**: you can `open` the built `.app` and `screencapture` it for real visual QA — that's expected and useful (see docs/specs/S02, S03 decision records for the pattern: a temporary `#if DEBUG` env-var hook to jump straight to the screen you're testing, removed before committing). But this machine is a real desktop the user is actively working on, and synthetic mouse clicks (`CGEvent` or otherwise) risk landing on the user's own windows instead of yours — don't do click-based UI automation here. Interactive behavior (does the toggle persist, does the button open Finder) gets verified by code review + unit tests instead, flagged for the user to click through themselves when convenient. Also: `NSStatusItem` (the menu bar icon) has been observed positioning itself off-screen on this particular machine (see S03's decision record) — that's an environment quirk, not a code bug, but it means "menu bar icon is visible" can't be confirmed here and needs a real, non-remote Mac before S21 ships.

**Microphone TCC permission cannot be genuinely tested on this machine** (see S07's decision record) — triggering the mic permission prompt showed a dialog for **"Air"** (the host agent environment), not "KnowingYou": the ad-hoc debug binary's TCC identity attributes to its process ancestry here, not to the app being tested. So it's not just "no one's around to click Allow" — clicking it would grant the wrong process the permission and wouldn't validate anything real. (Don't bother trying to dismiss a stray TCC dialog with synthetic input either — it's hardened against that by design and just ignores it; if one's left on screen it's harmless and just needs one real click.)

**Surprising counterpoint, confirmed by the S06 spike**: system-audio Process Tap capture (`AudioHardwareCreateProcessTap` → private aggregate device → `AudioDeviceCreateIOProcIDWithBlock` → `AudioDeviceStart`) works on this machine with **zero permission prompt**, and really captures real audio (verified: played a system sound, captured it, confirmed non-silent peak at the right timestamp). `Permissions.systemAudioProbe` should gate on `AudioDeviceStart`'s result, not just tap creation, since creation alone returned `noErr` here even in a context with no real "granted" permission state to speak of.

**But (S08 finding): don't create Process Taps repeatedly.** The very first tap creation in a session is instant. Every subsequent one in the same session got dramatically slower — 90 to 180 seconds — looking like a macOS anti-abuse throttle on repeated Process Tap creation. This is real and reproducible (happened both inside `xctest` and in the plain app binary), not a test-parallelism artifact. Concretely: `probePermission()`/`SystemAudioTap.start()` must not be polled or called speculatively — call once when actually needed and cache the result. `SystemAudioTapTests` intentionally does NOT include a "create a real tap" test for exactly this reason (would make `make test` randomly take minutes) — real capture is verified once, manually, via the Debug menu's "录 10 秒系统音频到桌面" or the S06 spike tool, not on every test run. `SystemAudioTap.handleOutputDeviceChanged()` rebuilds the tap on output-device change, and could hit this same throttle in real usage — flagged as a known, undesigned-for UX risk (S08's decision record), still unaddressed as of S09.

**S09 (`RecordingSession`) inherits both constraints above and adds one more of its own**: mixing/pause/resume logic was written and compiles under Swift 6 strict concurrency, and its pure math (`Mixer`) is unit-tested, but the actor itself was never exercised against real audio in this environment — doing so requires exactly the mic capture that's blocked here. It also does **not** do the sample-accurate hostTime-based alignment or long-run clock-drift correction the original spec sketch called for; it uses a much simpler fixed 50ms-period drain-and-mix loop instead (see S09's decision record for why: writing complex alignment code that can't be verified anywhere in this environment was judged worse than a simpler, predictable version with a documented precision ceiling). Anyone picking this up on a real Mac should treat "does the mixed output actually stay in sync over a multi-minute recording" as an open question, not a solved one.

**S11's menu-bar popover confirms the `NSStatusItem` off-screen quirk again, from a new angle**: the real menu bar on this machine shows no KnowingYou icon at all (same root cause S03 already flagged), so real click-to-open, click-outside-to-close, and multi-monitor positioning are all unverified here. Oddly, `statusItem.button.window.frame` — what `PopoverPanel` uses to position itself — still resolves to a plausible on-screen rect even though the icon itself isn't visible, which let a temporary debug hook force-open the popover and get a real screenshot for layout QA (removed before commit, per the established pattern below). Don't read anything into that coincidence — it means the popover's *content* was visually checked against `07-menubar-popover.png`, not that its real click/positioning code path was.

**S12 (`MeetingDetector`) is fully unit-tested with a fake `ProcessObjectReading`, but has never run against a real meeting app** — this machine has none of the whitelisted apps installed (Zoom, 腾讯会议, 飞书, etc. — see S06's spike report), and even Chrome-based detection can't be exercised without joining a real call. Only 4 of the 11 native bundle IDs in `KnownApps.defaults` have been confirmed with `mdls` against a real install (Slack, Discord, WeChat, plus Chrome for browsers); the rest are best-guess public bundle IDs that need verification on a real Mac with those apps installed before relying on them. `CoreAudioProcessObjectReader` itself is a low-risk, direct port of the S06 spike's already-verified `who-uses-mic` enumeration.

**S13 (`MeetingCoordinator`) depends on two new narrow protocols — `MeetingRecordingControlling` and `MeetingNotifying`** (implemented by `AppState` and `Notifier` respectively) instead of those concrete types, specifically so `MeetingCoordinatorTests` could inject fakes and avoid both the mic-TCC wall (`AppState.startRecording` needs real mic access) and real `UNUserNotificationCenter` calls. All 9 of the state machine's acceptance scenarios (①–⑨ in S13's spec) pass using a hand-rolled `ManualClock: Clock` — no real `Task.sleep` for the 3s/10s/20s delays anywhere in the test suite, which is why `make test` still finishes in well under a second with 87 tests. What's *not* verified: real Zoom/Chrome detection end-to-end, real notification banners actually appearing/disappearing, and the menu-bar red dot actually lighting up — all blocked by the same stacked constraints above (no meeting apps installed, no real menu bar icon, no real mic).

**S14 (`NotesMarkdown`/`NotesStore`) is the first spec since S02/S03 with essentially no environment-constraint gaps** — no mic, no menu bar icon, no meeting app needed, just pure text serialization and real (temp-directory) file I/O, so all its acceptance criteria are checked, not just code-reviewed. Two things worth knowing if you touch it: `render`/`parse` take an explicit `timeZone` parameter (default `.current`) specifically so the golden-fixture test isn't accidentally tied to this machine happening to be in `Asia/Shanghai` (which is what the plan's own example uses); and `NotesStore`'s autosave is a true per-edit debounce (cancel-and-reschedule), not a fixed-tick poll, which is both easier to test with a shrunk `autosaveInterval` and gives a tighter "at most N seconds after the *last* edit" latency bound than a poll would.

**S15 (`FloatingWidgetPanel`/`PillView`) also hit a second environment-specific crash, independent of the `nonisolated` one above**: constructing the `NSPanel`/`NSHostingView` eagerly inside `FloatingWidgetPanel`'s singleton `init()` crashed under the `xctest` host here (`applicationDidFinishLaunching` touches the singleton on every launch, including test launches, via `configure(onStop:)`). Fixed by deferring all real window/hosting-view construction to the first actual `show()` call (`ensurePanel()`) — `make test` now never creates a real `NSPanel` at all. If you add another borderless-panel-backed UI piece (S16's notes window is next), build it lazily from the start rather than discovering this the same way twice. Visual layout (5-segment level meter reading the right lit-segment count at a real level, all five W1–W5 elements at their exact spec'd positions) was confirmed via the same temporary-debug-hook-then-screenshot pattern as S11; real drag-to-reposition, real recording-triggered show/hide, and real fullscreen-meeting-app layering are all unverified for the usual reasons (mic TCC, no meeting apps installed).

## Common commands

The Xcode project (`KnowingYou.xcodeproj`) is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` and is gitignored — never edit it by hand, edit `project.yml` and regenerate.

```sh
brew install xcodegen   # one-time
make gen                # regenerate KnowingYou.xcodeproj from project.yml
make build              # gen + scripts/check-no-network.sh + xcodebuild build (Debug)
make test               # gen + scripts/check-l10n.sh + xcodebuild test (Swift Testing, KnowingYouTests)
make run                # build + open the built .app
make clean              # remove build output and the generated .xcodeproj
```

- `make build` and `make test` build the whole app, not a subset — there's no "build/test just this file" shortcut at this scale yet. To run a single test, use `xcodebuild test -scheme KnowingYou -destination 'platform=macOS' -only-testing:KnowingYouTests/PreferencesTests/someTest`.
- Debug builds sign ad-hoc (`CODE_SIGN_IDENTITY: "-"`); hardened runtime is disabled for ad-hoc signing (expected, not a bug). Real signing/notarization is S21's job, at release time only.
- `scripts/check-no-network.sh` greps `KnowingYou/` for networking APIs and fails the build if any are found — this is what makes "zero network" a build gate instead of a promise. If it fires on legitimate code, the answer is almost never to delete the check.
- `scripts/check-l10n.sh` fails if any key in `Resources/Localizable.xcstrings` is missing a non-empty English translation (S19) — run it any time you add a new user-facing string.

## How work is organized

Development is driven by the specs in `docs/specs/`. Start every coding session by reading [docs/specs/README.md](docs/specs/README.md):

- **Pick a spec** from its status table whose dependencies are all `done`, set its frontmatter `status` to `in-progress`, and update the table.
- **Work only inside that spec's "范围 › 做" scope.** Things it lists under "不做" belong to another spec — don't pull them in.
- **Shared types live in S00** (`docs/specs/S00-shared-contracts.md` → `KnowingYou/Support/Contracts.swift`). If you need a new cross-module type, preference key, or notification identifier, add it there first.
- **Definition of done** is in the README §1 — every acceptance checkbox verified, tests green, zero warnings under strict concurrency, `scripts/check-no-network.sh` passing, and the spec's status set to `done`.
- **Decisions go in the spec**, in its "决策记录" table, not in code comments or chat. Product decisions that are still open are listed as defaults in README §2; follow those defaults unless the user overrides them.
- Commit messages start with the spec ID, e.g. `S07: MicCapture device fallback`.

## What this project is

知鱼录音 (Knowing You) is a macOS menu-bar meeting-recording app. It detects when meeting software starts using the microphone and (automatically, or after confirmation) records both microphone and system audio. While recording, a floating widget lets the user jot timestamped notes. Output is a flat pair of files per recording: `<timestamp> <app name>.m4a` + same-named `.md` notes file, saved only to a local folder the user picks.

**Zero network**: no accounts, no cloud, no telemetry, no auto-update, no AI. This is the core product differentiator — verifiable with a tool like Little Snitch.

## Product scope discipline

The UI is being built as a near-pixel clone of a reference prototype (Plaud desktop). The rule when implementing any screen: **reproduce every element from the screenshots**, and only make three categories of change:
1. Remove network/account/cloud-sync/upload features (keep the layout slot, replace with a local equivalent)
2. Remove anything AI-related
3. Replace branding copy (Plaud → 知鱼录音 / Knowing You)

`docs/02-ui-spec.md` §12 has the full copy-replacement table and §13 the full removal list — don't improvise removals or additions beyond what's listed there. New elements not in the screenshots (e.g. save-path picker, audio format picker, start/stop-recording hotkey row) are called out explicitly in the spec as additions; anything else should stay visually identical to the reference.

### Key technical decisions to preserve

- **System audio**: Core Audio Process Tap (`CATapDescription(stereoGlobalTapButExcludeProcesses:)` — tap the whole system, exclude the app's own process — not per-process taps, which are less stable across multi-process Electron apps). Feeds a private aggregate device read via `AudioDeviceCreateIOProcIDWithBlock`. Do **not** point `AVAudioEngine` at the tap aggregate device directly — it silently falls back to the default input; must use the IOProc.
- **Meeting detection**: signal is "a known app is actively using the microphone," read via Core Audio process objects (`kAudioHardwarePropertyProcessObjectList` + `kAudioProcessPropertyIsRunningInput` + `kAudioProcessPropertyBundleID`), triggered by device-level `kAudioDevicePropertyDeviceIsRunningSomewhere` plus a low-frequency poll fallback — not calendar/EventKit, not "is the app merely running." On macOS 26 the property listener for `IsRunningInput` doesn't fire reliably, so polling is load-bearing, not optional. Browser-based meetings (Chrome, etc.) only ever prompt the user — never auto-record — since detection confidence is low (can only tell "Chrome is using the mic," not which site).
- **State machine** (plan §5.1): `idle → meetingActive` (whitelisted process using mic for 3s) → `recording` (if auto-record on) or a "start recording?" notification (if off) → `finalizing → idle` when the process stops using the mic for 10s. Manual start/stop always overrides the automatic flow.
- **Recording pipeline**: mic + system audio each resampled to 48kHz float via `AVAudioConverter`, aligned by buffer timestamp, mixed (mono by default; optional stereo dual-track = L mic / R system). Written live to `.caf` (crash-safe, appendable), transcoded to AAC `.m4a` on stop, then the `.caf` is deleted. A leftover `.caf` found at launch means offer crash recovery.
- **File naming** (plan §5.3): flat directory, no subfolders except when screenshot marks exist. Filename = `<start timestamp to the second> <triggering app display name>`. No in-app rename. Manual recordings with no detected meeting app are named "手动录音" (Manual Recording). The notes-window title field only writes into the `.md` frontmatter/heading — it never affects the filename.
- **Notes file**: Markdown with YAML frontmatter (`title`, `started_at`, `ended_at`, `duration`, `source_app`, `audio`, `paused`), body is a sequence of timestamped entries (`kind: note|mark|screenshot|event`) each stamped with wall-clock time + offset from recording start, captured at the moment the first character of an entry is typed. No separate JSON metadata file — "recent recordings" is produced by scanning the save directory and sorting by the filename timestamp.
- **Floating widget**: a single `NSPanel` that animates between a 70×270 "pill" state and a 418×380 "notes" state, anchored so the top-right corner stays fixed. `nonactivatingPanel`; the pill never takes keyboard focus, the notes state uses `becomesKeyOnlyIfNeeded` so it only becomes key when a text field is clicked (app itself never activates/shows in Dock from this). `.floating` level with `canJoinAllSpaces` + `fullScreenAuxiliary` so it can sit above fullscreen meeting apps.
- **Permissions are requested lazily**: microphone + system-audio-capture on first recording, notifications at first-run onboarding, screen recording only the first time the screenshot-mark feature is used. No Accessibility permission is needed (the hotkey library uses Carbon hotkeys, not AX).
